# Контракт `GET /robot-api/v1/labels`

Что должен отдавать портал, чтобы `bisquite-teleport` применял на машине
метки `space` и `env`. Контракт — версия 1; агент проверяет его строго, и
любое отличие формы ответа — отказ без записи.

Портал — любой сервис, который знает, в каком пространстве (`space`) и
окружении (`env`) должна быть машина. Пример реализации — портал Stvor.

## Включение на машине

```bash
read -rs T && printf '%s' "$T" | sudo bisquite-teleport labels-enable URL=https://<портал>/robot-api/v1/labels; unset T
```

- Адрес — ровно `https://<хост>[:порт]/robot-api/v1/labels`
  (`^https://[a-z0-9.-]+(:[0-9]{1,5})?/robot-api/v1/labels$`); другой путь,
  `http://` или кавычка в адресе — отказ.
- Токен — 43 знака `[A-Za-z0-9_-]` (32 байта в base64url без `=`), читается со
  stdin; пробелы и перевод строки по краям отбрасываются. Токен выдаёт портал
  на одну машину; повторный `labels-enable` с новым токеном — перевыпуск.
- Токен и адрес лежат вместе в `/etc/bisquite/teleport/labels-token` (0600,
  root): строки `url=…` и `token=…`. В argv, `status` и журнал токен не
  попадает: `curl` получает заголовок из файла (`-H @файл`).

## Запрос

Раз в минуту (`bisquite-teleport-labels.timer`: `OnBootSec=1min`,
`OnUnitActiveSec=1min`, `RandomizedDelaySec=20s`):

```
GET <TELEPORT_LABELS_URL>
  Authorization: Bearer <токен>
  If-None-Match: "<ревизия>"        # если ответ уже запомнен
  X-Applied-Revision: <ревизия>     # только вместе с If-None-Match той же ревизии
```

`X-Applied-Revision` уходит, только когда ревизия действительно действует:
ручки несут ожидаемые метки, перезапуск агента подтверждён, агент активен.
Портал узнаёт о применении на следующем тике и по нему может завершать
перенос машины между пространствами.

Редиректам `curl` не следует; таймауты — 30 с на запрос.

## Ответ

| Код | Тело | Что делает агент |
|---|---|---|
| `200` | `{"labels":{"env":"<v>","space":"<v>"},"revision":"<16 hex>"}` | проверяет тело целиком, запоминает, применяет |
| `304` | — | ничего не скачивает; сверяет ручки с запомненным ответом |
| `401`, `429`, `3xx`, `5xx`, сеть | — | одна строка в журнале, код 0, ничего не тронуто; повтор — следующий тик |

Тело `200` — **компактный JSON, ключи ровно в этом порядке**, каждый один раз:

```json
{"labels":{"env":"prod","space":"sp-1a2b3c4d"},"revision":"0123456789abcdef"}
```

- `env`, `space` — `^[a-z0-9][a-z0-9-]{0,62}$` (алфавит метки DNS: в значение
  не пролезают кавычка, запятая, `=` и перевод строки);
- `revision` — `^[0-9a-f]{16}$`, меняется при любом изменении меток;
- тело не длиннее 4096 байт, без NUL.

Иначе — отказ (код 1 у `pull`), ничего не записано.

## Что агент делает с ответом

- `space` заменяет элемент `space=` в `TELEPORT_LABELS` на его месте (прочие
  метки оператора остаются), `env` — значение `TELEPORT_ENV`.
- Изменение применяется **одним перезапуском** `teleport.service` (не HUP):
  узел и все его веб-приложения переезжают в новое пространство вместе,
  открытые SSH-сессии прежнего пространства рвутся.
- Сверяется состояние, а не ревизия: на каждом тике (и на `304`) ручки
  сравниваются с последним ответом портала; расхождение (ручной `set`,
  повторный firstboot, неудавшийся перезапуск) исправляется.
- После трёх неподтверждённых перезапусков подряд, пока агент активен, тик
  перезапускает его не чаще раза в 15 минут.

## Чего портал сделать не может

- Доставить код на машину: агент принимает только два значения из
  фиксированного алфавита.
- Поменять кластер, токен регистрации, приложения и прочие метки.
- Задать метки `app`, `managed_by`, `os_logins`, `teleport.icon`.

Портал при этом — источник правды о доступе: сменив `space`/`env`, он
переносит машину между пространствами, и роли кластера дают доступ по новым
меткам.

## Метка способа установки

Агент ставит узлу метку `managed_by=bisquite-teleport-agent`. По ней портал
может отличать машины с агентом от машин с `teleport.yaml`, написанным
вручную. Метка — часть контракта и не переименовывается.
